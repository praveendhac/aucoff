## Blockers and Notes
- **Authentication-everywhere (ZT-1) gap in the first scaffold is fixed for the backend and the Helm chart** (T-120 done, T-124 partly done on 2026-10-19). Still open: enforcing the same default-deny in the frontend BFF route handlers (T-301), per-service database and broker credentials (T-122, T-123) and authenticated telemetry.
- **v1 scope decision:** v1 (MVP) is local-only on kind; AWS/Terraform/EKS work (T-501, T-502) is deferred to post-v1 and does not gate any v1 task.
- **Findings during Session 2 (2026-10-19):** (1) ingress-nginx is retired - Traefik used; (2) CloudNativePG's *standard* PostgreSQL image bundles pgvector 0.8.7 that shadows the pinned extension image - the minimal image is used so pgvector is exactly 0.8.6; (3) CloudNativePG always appends a catch-all scram rule, so TLS is enforced with `hostnossl ... reject`; (4) a new pod's DNS/egress is blocked until the NetworkPolicy that allows it exists - the DB-client egress policy is a pre-upgrade hook, and the migration retries the connection; (5) the audit hash chain had a concurrency ordering race, fixed with a per-tenant `chain_pos`; (6) psycopg is LGPL, so asyncpg is the only PostgreSQL driver.
- **Laptop ready (2026-10-19):** kind v0.33.0 installed, Colima running with 6 CPUs / 12 GiB; the local cluster comes up with `make up` and `make smoke` passes.
- **Laptop prerequisites found 2026-10-19:** Docker is installed but its Colima daemon is stopped (`colima start`), and `kind` is not installed (`brew install kind`); `make doctor` reports this. T-004 and `make cluster-up` need both.
- T-004 (pre-build verification) can change version pins and the Postgres/pgvector image (pgvector 0.8.6 with PostgreSQL 18.6 is owner-confirmed; image and operator support still to verify); do it before the T-002 scaffold is finalised.
- T-009 (licence and provenance audit) gates T-007, T-405, T-407 and the scanner choices; no tool or image is adopted until it passes constitution LIC-1 to LIC-5.
- T-006 (unified control set authored by owner) gates meaningful scanner-to-control mapping and mapping-agent evaluation.
- Items marked TODO in other specs are tracked in each spec's open-questions section; deferred ones (brand, locales, KEDA, mTLS, image signing, plan limits) do not block the build.
- **Findings during Session 3 (2026-10-19):** (1) Keycloak imports the realm only when it does not exist yet - to apply a realm change locally, delete the realm (or drop the `keycloak` database) and restart the pod; (2) Keycloak's `start` needs a writable root filesystem, so that one container does not set `readOnlyRootFilesystem` (all other hardening applies); (3) its probes are TCP checks because the management port (anonymous health) is deliberately not enabled; (4) the expired-token case is tested for real with a smoke client whose tokens live 5 seconds; (5) the throwaway smoke clients exist only when `smokeClients: true` (local values); (6) the temporary Keycloak bootstrap admin is reachable only through `kubectl port-forward` and must be replaced by a named admin before any shared use; (7) not yet done: RabbitMQ (T-123), the Auth.js login (T-301), image vulnerability scan and SBOM (T-010), authenticated metrics/telemetry.
- **Findings during Session 4 (2026-10-19):** (1) browsers must reach the issuer, so Keycloak's public hostname is `idp.localtest.me:8443` (port-forward) while pods use the service name - tokens carry the public issuer; (2) Auth.js v5 is still beta, v4.24.15 is used; (3) the ingress previously sent all `/api` to the backend, which would have captured Auth.js - only `/api/v1` goes to the backend now; (4) `npm install` after adding a dependency broke the vitest native binding until `node_modules` and the lockfile were regenerated; (5) the session cookie is not `Secure` over the local plain-HTTP ingress.
- **Findings during Session 4, messaging (2026-10-19):** (1) RabbitMQ loads users and permissions from a definitions file at boot, so the file (with generated passwords) is a Secret made by `make secrets`; changing it needs a broker restart; (2) with definitions loaded the broker creates no default `guest` user; (3) routing keys start with the sender (`work.<sender>.<recipient>.<type>`) so topic permissions restrict who may speak as whom, and the broker itself rejects a wrong `user_id`; (4) services cannot declare queues or exchanges - those are created from the definitions; new services must be added there.
- **Findings during Session 4, image scan (2026-10-19):** (1) `node:22-slim` (Debian 12) carried 7 fixable perl HIGH/CRITICAL findings with no fixed image, so the frontend moved to `node:24-trixie-slim`; (2) pip/setuptools (python) and npm (node) are bundled in the base images with vulnerable vendored libraries and are not needed at run time, so they are deleted from the final images; (3) Trivy matches the local `sharp` stub by name, so four advisories for the real library are ignored with a written reason in `.trivyignore`; (4) the scan uses the Trivy vulnerability database downloaded at scan time, so results change over time and must be re-run.
- **Branch protection not applied (2026-10-19):** the owner approved the rules (PR required, checks backend/frontend/helm/secrets, no force-push or deletion, admins not enforced), but the GitHub CLI on this laptop is logged in as another account (`praveenda_Zeta`) that has read-only access to `praveendhac/aucoff`, so GitHub answered 404. The owner must run the two commands in the README with an admin account.
- **CI correction (2026-10-19):** earlier notes said the workflow had never run; it had, and the frontend job failed from the Session 4 push until now because `frontend/src/lib/` was hidden by the `lib/` rule in `.gitignore` and Next's generated route types were missing in a clean checkout. Both are fixed; all four jobs are green on commit `29a3e85`. Lesson: check `gh run list` after each push.
